# T-157: run dump regressions as Python tests over the built ay binary

## Scope and current mechanism

The build graph currently has one `go_test` command for every Go regression in
the root package.  Its input set is also shared with the production `ay` node,
so `*_test.go` files unnecessarily invalidate the production binary.  The
dump command regressions call `cmdDump*` functions in-process even though the
same behavior is fully observable through the shipped command-line interface.

This ticket introduces the minimal reusable shape for binary-level tests and
migrates `dump_test.go` and `dump_diff_test.go` completely.  It does not shard
one Python suite, invent thematic suites, add a test protocol to `ay`, or
change any production behavior.

## Build graph

`build.py` will split Go inputs into production and test files.  `ay` will
depend only on production Go sources; the remaining `go_test` node will depend
on both sets.

Every `tst/test_*.py` file will become one addressable command node by a small
loop in `build.py`:

- input: that test file and `tst/lib.py`;
- dependency: the existing `ay` target;
- output: `$(B)/tests/<name>.stamp`;
- command: run the test file with `AY_TEST_BINARY` pointing at
  `$(B)/bin/ay`, then touch the stamp;
- aggregate membership: `unit` and `test` through the existing group lists.

The file is the build entity.  There is no method discovery or fixed shard
count in `build.py`; the build engine can run independent files concurrently.

## Test harness and observable behavior

`tst/lib.py` will contain only the common subprocess operation needed by these
tests: resolve `AY_TEST_BINARY`, invoke it with captured stdout/stderr and a
finite timeout, and fail with the complete command output.  Individual tests
own their temporary directories and fixtures through the Python standard
library.

`tst/test_dump.py` will reproduce every regression from `dump_test.go` and
`dump_diff_test.go` through the public commands:

- `ay dev dump normalize`;
- `ay dev dump sort`;
- `ay dev dump diff`;
- `ay dev dump grep`.

The expected JSON/text values remain those of the existing tests.  Helpers for
constructing small graph lines remain local to `test_dump.py`; they are test
data, not an alternative implementation of dump normalization or comparison.
The two original Go files will be removed only after the Python node passes.

## Implementation sequence

1. Commit this plan before changing code.
2. Split production and test Go inputs in `build.py`; add automatic binary
   test nodes and wire them into `unit` and `test`.
3. Add `tst/lib.py` and a focused self-test only if behavior beyond a direct
   `subprocess.run` wrapper is introduced.
4. Port all tests from `dump_test.go` and `dump_diff_test.go` without changing
   their assertions, then run the new node while both Go files still exist.
5. Remove the two Go files, rerun the new node and the remaining Go tests, and
   commit the completed slice.

## Validation and expected gate effect

The production binary must be byte-identical before and after the build-graph
input split.  The new Python dump node must pass directly and on a cached
second invocation.  `./build unit` must pass after removal of the Go files.
Finally, run the full foreground `./build test`; validation status and parity
must be unchanged because no graph-generation code is modified.

Measure an uncached `unit` run before and after the completed slice.  The
migration must not regress wall time outside the 5% noise band.  The expected
direction is a smaller Go test compilation unit with cheap binary invocations
running as an independent node.
