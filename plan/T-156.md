# T-156: eliminate ranking_middlesearch parity differences

## Baseline and scope

`search_daemons_ranking_middlesearch` currently reports 45,508 matched nodes,
51 `our-only`, and 51 `ref-only` nodes.  The 51 pairs are real; they are not a
validator ordering artifact.  Most are UID propagation from a small set of
primary content differences:

- `RUN_PROGRAM` output-include closure for `gen_types.h`;
- `DECLARE_IN_DIRS(... SRCDIR ${ARCADIA_ROOT})` expansion;
- `DISABLE(PROTOC_TRANSITIVE_HEADERS)`;
- induced dependencies of per-output C++ proto plugins;
- `RESOURCE` lookup through `SRCDIR`;
- five `$AUTO_INPUT` archive-member ordering differences.

The work must not add fields to `GeneratedFileInfo`, `SrcMeta`, `ModuleData`, or
the AST, and must not introduce a side channel.  Include resolution remains a
function of the included file alone and remains cacheable under its current VFS
key.  Existing parsed results, the codegen registry, declared-producer
scheduler, and emitted graph nodes are the only sources of information.

## Upstream mechanisms

### `OUTPUT_INCLUDES`

`devtools/ymake/macro_processor.cpp` attaches parsed `OUTPUT_INCLUDES` to every
artifact of a command.  `add_node_context.cpp::ApplyOutputIncludes` then
applies the normal processor selected by the output's file type; for a C/C++
header this creates ordinary include edges, while an unsupported output type
falls back to direct induced-dependency edges.

Whether those edges also become inputs of the exported command node is a
consequence of upstream graph topology.  A non-final command with one output
uses that output node itself as `actionNode`, so its `OUTPUT_INCLUDES` closure
is traversed while collecting the command's JSON inputs.  A command with more
than one output gets a separate `$L/ACTION/<main-output>` node.  The real
outputs, each carrying the same output-include property, hang from it through
`EDT_OutTogetherBack`; `json_visitor.cpp::AcceptDep` deliberately does not
traverse those back edges.  Thus the shared multi-output command gets only its
direct inputs, while consumers of each artifact still get the artifact's
include closure.

`gen_types.h` is the sole output of its `RUN_PROGRAM`, so its source include
closure participates in the PR inputs despite the explicit `IN company.in`.
`GENERATE_ENUM_SERIALIZATION` is irrelevant to that producer input set.  The
large caesar and cow generators are multi-output commands, explaining why
their reference PR nodes do not contain their output-include closures.

### `DECLARE_IN_DIRS`

The implementation in `build/ymake.core.conf` explicitly permits `SRCDIR` to
start with `${ARCADIA_ROOT}`.  Variable expansion has already converted that
token to `$(S)` by the time ay applies the statement.  `$(S)` is therefore the
expanded spelling of the existing source-root mode, not a new directory kind.

### transitive proto headers

`build/ymake.core.conf` tests `PROTOC_TRANSITIVE_HEADERS == "no"`.  In that
branch it adds `proto_h=true` and `.deps.pb.h` to the C++ protoc invocation and
outputs.  `DISABLE(PROTOC_TRANSITIVE_HEADERS)` writes the same variable value as
the corresponding `SET`; ay currently changes only its evaluation environment
and loses the value before proto emission.

### per-output proto-plugin induced dependencies

`build/conf/proto.conf` adds each `CPP_PROTO_PLUGIN` tool and its declared
outputs to the protoc command.  In ymake, output-specific dependency rules are
attached by output type/name in `macro_processor.cpp` and applied by
`ApplyDepRules`; a plugin tool's `INDUCED_DEPS(h ...)` belongs to that plugin's
generated header, not to the core `.pb.h`/`.pb.cc` outputs of the same protoc
command.  Ay currently puts every plugin tool in `pbGenRefs`, so scanning core
`.pb.cc` reaches unrelated capability/apphost header closures.

The existing registry already models output-specific information for YAFF,
gRPC, and the core outputs.  The observed divergence is on core `.pb.cc`
consumers: ay attaches the induced-header closure of plugins that declare their
own output suffix, while reference does not.  Plugins without a suffix
(`CPP_PROTO_PLUGIN0`) emit into the regular core outputs and therefore remain
core generator refs; plugins with their own suffix do not.  The protoc command
node itself still depends on every tool.

The validation target contains no consumer of the affected `.cap.h` or
`.apphost.h` plugin outputs, so this ticket will not invent registry entries for
them.  An attempted general registration changed lazy materialization and
regressed parity by thousands of nodes, proving that it is not the counterpart
of upstream output rules.  Output-consumer modelling requires a separate
upstream-backed seam; it is outside this divergence.

### `RESOURCE` and `SRCDIR`

Static `RESOURCE` file operands use the module's normal source resolver in
ymake, including `SRCDIR`.  Ay's resource emitter currently falls back directly
to a module-relative source path.  It must call the same existing source
resolution path used by other emitters, with the module's existing `srcDirs`.

### archive member order

`TModuleDef::StatementPriority` gives ordinary generating statements priority
2 and `SRCS` priority 4.  `TModuleBuilder::RecursiveAddInputs` processes its
command queue FIFO: a command whose generated input is unavailable moves to the
tail; successful commands expose their outputs and enqueue downstream work.
`mkcmd.cpp` preserves the resulting module `BuildFrom` edge order in
`$AUTO_INPUT`.  There is no array permutation in upstream.

Ay already has the counterpart mechanisms:

- `producerPositions`/`scheduleProducers` establish real producer edges before
  emission;
- `resolveNodeCodegenDeps` attaches registered producers to consumers;
- `StreamingEmitter` retains every emitted producer node, including its real
  command class (`PB`, `R6`, `BC`, and so on);
- `SrcMeta` already contains upstream statement priority and declaration
  sequence, and `reorderARMembers` already uses them.

The missing distinction will be reconstructed from those existing nodes, not
transported through new metadata.  A generated compile is one FIFO round later
when its source producer consumes an in-module generated source (for example
`GZ -> PB` or `PR -> R6`).  A `BASE_CODEGEN` output is already available in the
priority-2 declaration round before the following enum generator and therefore
does not add a round.  That boundary will be derived from the actual producer
node/class already retained by `StreamingEmitter`; it will not be represented
by a new flag.  The expected orders are:

- direct C++ objects, enum serialization, direct `.rl6`, generated `.rl6` in
  `kernel/dater`;
- `calcer_codegen.h_serialized` before `merge.h_serialized` because the former's
  `BC` producer precedes both enum statements;
- direct proto objects before `gztproto -> proto` objects;
- direct proto objects, then enum serialization of a generated `.pb.h`, then
  the later gztproto object in `porn_query`.

## Test-first implementation sequence

Each item starts with a focused test that fails on the current tree for the
identified content difference.  Fixes are committed separately so the
validation movement is attributable and reversible.

1. **`RUN_PROGRAM` output includes**
   - Use an `emit_pr_test.go` fixture with explicit `IN`, exactly one generated
     header output, and `OUTPUT_INCLUDES` whose external header has a transitive
     include.  No consumer is needed to trigger the upstream behavior.
   - Assert that this single-output PR producer contains the full source
     closure.  Keep the existing two-output `gen.h + gen.cpp` fixtures as the
     counterexample: their shared PR producer must remain direct-input-only,
     while their generated artifacts still expose the closure to consumers.
   - Derive the one-output topology locally from the existing `RunProgramStmt`
     output lists.  In `prInputClosure`, route that case through the existing
     scanner and codegen registry exactly as the already supported single-output
     `.cc` cases do.  Do not inspect consumers, introduce a field, add a side
     channel, recompute an include closure, or alter the scanner cache key.
   - Expected isolated validation movement is six repaired normalized-node
     pairs: matched `45,508 -> 45,514`, gaps `51/51 -> 45/45`, with no newly
     unmatched nodes.

2. **Expanded source root in `DECLARE_IN_DIRS`**
   - Add a module test where the directory list variable is expanded and
     `SRCDIR` is `${ARCADIA_ROOT}`/`$(S)`.
   - Assert that all declared files and command arguments resolve at source
     root.
   - Change `modules.go` to recognize the existing expanded source-root VFS
     spelling.

3. **`DISABLE(PROTOC_TRANSITIVE_HEADERS)`**
   - Add a proto emitter test asserting `proto_h=true` and `.deps.pb.h` after
     `DISABLE`.
   - Route the disabled variable value into the existing `setVars` store in
     `modules.go`, exactly as `SET` already does.

4. **Per-output proto plugin rules**
   - Add a proto/scanner test with a plugin tool carrying `INDUCED_DEPS(h ...)`.
     It must prove that the core `.pb.cc` does not receive the induced closure
     of a plugin with its own output suffix.
   - Refactor `emit_proto.go` so `pbGenRefs` keeps core tools and suffix-less
     plugins, while excluding plugins with separate outputs.  Do not register
     new outputs, alter existing YAFF/gRPC entries, or change lazy emission.

5. **`RESOURCE` source resolution**
   - Add an emitter test with `SRCDIR` and a static resource operand.
   - Resolve it through the existing `resolveSourceVFS` path in
     `emit_resource.go`.

6. **FIFO-derived archive ordering**
   - Add focused failing graph tests for `PR -> R6`, `GZ -> PB`, generated-pb-h
     enum serialization, and `BC -> EN`.
   - Refactor `gen.go::srcRound` to walk the already emitted producer graph.
     Use existing registry links only to locate producer refs; use the retained
     producer nodes to determine whether the upstream command entered a later
     FIFO round.  Do not populate new `SourcePath` values merely for ordering
     and do not add a boundary flag.
   - Keep `SrcMeta.sortKey` as `(round, StatementPriority, declaration seq,
     bucket)` and keep the stable sort.

## Validation and performance

After every implementation commit, rebuild
`validation_result_search_daemons_ranking_middlesearch` and compare both the
aggregate parity and the remaining primary pairs.  Expected monotonic movement:
matched rises, both gaps fall equally, no existing matched node disappears.
The target for this ticket is 45,559 matched and zero differences for the case.

Run focused Go tests after each red/green cycle, then `./build unit`.  Finally
run the full foreground `./build test`.  The final report must show no gating OK
loss, no new XFAIL, and no decreased `parity.matched` for any existing XFAIL.
Compare generation timing to the pre-change report; a slowdown above the 5%
noise band is a regression and must be removed before completion.
