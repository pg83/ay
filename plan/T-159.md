# T-159: migrate observable graph regressions file by file

## Scope and boundary

The binary-test graph and `tst/lib.py::make` path are now proven by the dump
and source-resolution slices.  This ticket performs the mechanical migration
of graph-generation regressions that are observable in the JSON emitted by
the production `ay make -j0 -G` command.

Existing Go test files remain the unit of work.  A file such as
`emit_archives_test.go` maps to `tst/test_emit_archives.py` and therefore to the
automatically discovered `unit_emit_archives` build node.  There are no manual
suites or shards.  A Go file is deleted when every assertion it contains is
visible in the public graph; mixed files retain only their genuinely
white-box tests.

This ticket does not migrate allocator/container tests, parser chunk-boundary
tests, cache lifetime tests, raw emitter calls before finalize, or concurrency
internals.  Those facts have no production-binary observation point and stay
under the existing `go_test` node.

## Observable mechanism

Every migrated test uses the same production path:

1. materialize the existing `newMemFS` file map under a temporary source root;
2. run the built `ay` with fixed Linux platforms, `-j0 -G`, and `--sandboxing`;
3. parse the emitted graph;
4. locate nodes by output or `kv.p` and assert their serialized `inputs`,
   `deps`, `cmds`, `env`, `outputs`, and ordering.

Serialized dependency UIDs replace assertions about internal `DepRefs`:
producer and consumer are located by output, then the producer's emitted UID
must occur in the consumer's `deps`.  No new data is passed through production
types, no second parser or resolver is introduced, and no expected result is
computed by duplicating ymake logic in Python.

`tst/lib.py` may gain only small observation helpers when at least one migrated
file uses them: node lookup by output, dependency lookup, and command argument
flattening.  Fixture writers remain in the test file unless reused by more
than one file.

## File order

Work from small, self-contained emitters toward the shared large emitters so
the harness grows only in response to real use:

1. archives and bundle/resource wiring;
2. small generators (`flatc`, `flex`, `gperf`, `sc`, `lua_run`, `copy`,
   `split_codegen`, `base_codegen`);
3. generated proto variants (`gztproto`, `ymaps_sproto`, `cfgproto`, proto
   descriptions, Python proto);
4. `RUN_PROGRAM` and ordinary proto;
5. the shared CC/AR/LD and top-level `gen`/`modules` regressions.

Within each file, first run the Python node while the Go assertions still
exist.  Remove only the covered Go methods, rerun the Python node and
`go_test`, then commit and push that finished file.  If an assertion depends
on an internal pre-finalize distinction not present in JSON, leave it in Go
and record that boundary in the commit message rather than adding a test hook.

## Gate and performance

After every file, run its addressable Python target and `./build unit`.
Periodically, and before completing the ticket, run the full foreground
`./build test`.  Production sources are unchanged, so every validation status
and parity count must remain identical: ten OK cases, one existing XFAIL, no
FAIL, middlesearch at 45,559 exact nodes, and no decrease in the XFAIL matched
count.

Track the uncached residual `go test` wall time and the runtime of each new
Python node.  The aggregate unit gate must not regress outside the 5% noise
band; split a Python file only if its natural file-level node becomes a proven
bottleneck.
