# Tree: файловый кеш дерева исходников

Статус: дизайн согласован 2026-11-19, реализация идёт по этапам (см. конец документа).

## Задача

Для заданного дерева исходников получать один файл (образ) с быстрым доступом. При следующем
построении графа по образу и diff между состоянием на момент сборки образа и текущим деревом
работа сокращается: в FS ходим только за тем, что изменилось. Цель — и быстрее, и меньше памяти;
в идеале память уходит только на новые структуры.

## Замеры (HEAD 0835e52, in-memory indexed FS)

| | sg5 (ydb/apps/ydbd) | p12 полный |

| вызовов интерна | 0,83 млн | 23,1 млн |
| прочитано файлов | 50 тыс. / 625 МБ | 503 тыс. / 4,55 ГБ |
| listdir | 7,2 тыс. (82 тыс. имён) | 328 тыс. (1,46 млн имён) |
| ya.make | 2,2 тыс. / 2 МБ | 103 тыс. / 60 МБ |
| файлов через парсеры include | 47,6 тыс., 296 тыс. директив | 307 тыс., 1,77 млн директив |
| резолв детей | 72,6 тыс. файлов, 467 тыс. id | 1,40 млн файлов, 6,9 млн id |

CPU на p12 (36,4 с user, maxrss 7–8 ГБ, с `-G`): GC mark 17,6%; замыкания (`dfs`) 13,6%, из них
резолв детей 8,2%; интерн около 7%; `readPath` 4,5% (3,8% — content-hash); разбор ya.make 3,3%;
парсер include 1,1%; listdir и walk около 2%.

Выводы:

- На in-memory FS работа, производная от файлов, — порядка 10–12% CPU. На реальном дереве это
  503 тыс. open/read/close и 328 тыс. getdents; время на FUSE не мерилось.
- Интерн-таблица — около 1,1 ГБ кучи на p12 (байты 567 МБ, `flatStr` 114 МБ, `cells` 170 МБ,
  `flatLo` 57 МБ, `ids` около 200 МБ). `flatStr` и `cells` содержат указатели и сканируются GC.
- Бакеты замыканий — 504 МБ кучи.

## Модель

Tree — одна структура из двух слоёв:

- **Образ**: замороженные run-wide таблицы, mmap только на чтение, ключи — id строк.
- **Оверлей**: те же таблицы в куче для новых и изменённых ключей.

Выбор слоя — один бит на ключ: «в образе есть и diff его не задел». Битсеты готовятся при
загрузке за O(|diff| × глубина пути). Обычный режим — тот же Tree с пустым образом: один путь
кода, гейт гоняет то же, что и кеш-режим. Сборка образа — прогон с записью на выходе оверлея
плюс валидной части старого образа; инкрементальное обновление получается тем же путём.

Tree — конкретная структура, а не Go-интерфейс с двумя реализациями: обычный режим не платит за
диспетчеризацию на горячих путях. Нынешний `FS` остаётся бэкендом под оверлеем (OsFS, indexed,
MemFS).

Типы слоёв не смешиваются (решение 2026-11-19): у каждой секции образа свой read-only тип
(`Mmaped*`), который знает, что лежит поверх неизменяемых байт, и не имеет изменяющих методов.
Изменяемые контейнеры (`IntMap`, `DenseMap` и прочие) живут только в оверлее и поверх mmap не
строятся. Запись секции свободна: может заглядывать во внутренности контейнера и писать его
массивы как есть.

## Строки

Копий нет: mmap образа и новые строки лежат в одном виртуальном диапазоне.

- Резервируется большой диапазон адресов под байты строк. В начало маппится секция образа,
  хвост — анонимная память под новые строки.
- Таблица `id → (смещение, длина)`, 8 байт на строку, устроена так же: начало из файла, хвост
  растёт. `string()` — одна загрузка 8 байт и сложение, без ветки, одинаково для старых и новых.
- Массив `lo` (вторая половина xxh3-128, он же uid-хеш строки) — так же.
- Хеш-индекс двухуровневый: замороженная open-addressing таблица из файла (`MmapedIntMap`, только
  `get`) плюс обычный `IntMap` для новых строк. Попадание в образ — одна проба, новая строка —
  две. В замороженную таблицу не пишем: copy-on-write запачкал бы её страницы.
- Массивы не переезжают, поэтому lock-free читатели (uid-воркеры) читают их напрямую; `cells`
  (PageVec) не нужен. Это верно и без образа.
- Привязка к бинарю: id констант из `*_consts.go` должны совпасть с началом образа. Проверка —
  сравнение `lo` первых K строк; при несовпадении образ не используется. Таблицы ARG и ENV в
  образ не идут, пока ни одна секция не хранит их id (токены ya.make и директивы хранят STR).
- Вне Linux: секции читаются в тот же диапазон копией на старте.

В образ идёт вся таблица прогона (вариант A, решение 2026-11-19): заморозка — дамп как есть,
повторный прогон не копирует ни одной строки. Следствие: id-пространство прогона на подмножестве
целей равно id-пространству образа; этот случай пока не оптимизируется.

## Что лежит в образе

| Секция | Ключ | Инвалидация по diff |
|---|---|---|
| строки, индекс, `lo`, ARG/ENV | id | нет, только дописывается |
| листинги (имена с битом каталога и режимом) | каталог | A/D: перечитать родителя |
| content-hash | файл | M/A/D |
| директивы include и вид парсера | файл | M/A/D |
| токены ya.make и `.inc` | файл | M/A/D |
| мемо `resolveSourceUnder(prefix, target)` | пара id | A/D, по разбиениям пути |
| индекс ADDINCL (target → каталоги) | target | A/D: точечная правка |
| дети, search tier | файл / (хеш конфига, target) | см. «Резолвы» |
| бакеты и списки замыканий, обратные рёбра | файл | см. «Резолвы» |

- ya.make: AST на интерфейсах в mmap не положить; кешируется поток токенов с id. Убираются
  чтение, лексер и интерн токенов, AST строится в кучу как сейчас.
- `build/` и conf идут в FS напрямую. Сырые чтения (package.json, lock-файлы, бандлы) — тоже;
  на p12 их около 90 тыс., посчитать отдельно.
- Замороженные данные неизменяемы: изменяемые пометки (ячейка эпохи перед бакетом и подобные)
  живут в боковых массивах.

## Diff

Контракт: полный список путей, чьё состояние отличается от базового, со статусом A/M/D. Образ
хранит идентификатор базы.

Источники (решение 2026-11-19):

1. Сначала diff приходит снаружи, полнота — ответственность клиента.
2. Потом развилка по клиентам. Для срезов репозитория вне VCS кеша нет (или diff — задача
   внешнего клиента). Если есть `.arc`/`.git`, в образ пишется commit, и diff строится самим ay
   в расчёте на то, что git/arc делают это быстро.

Применение при загрузке:

- M: сбросить бит валидности файла (content-hash, директивы, токены).
- A/D: то же для самого пути; листинг родителя перечитывается из FS; разбиения пути по слешам
  сбрасывают записи мемо `resolveSourceUnder` и правят индекс ADDINCL.

## Резолвы

Результат резолва директивы зависит от: директив файла; каталога включающего файла;
search-конфига (ключ — хеш содержимого, не `num`); существования каждого кандидата
`prefix/target`; реестра сгенерированных файлов; конфигов sysincl; того, какой контекст дошёл до
файла первым.

Уровни по нарастанию риска:

- **R0** — резолвы не кешируются, считаются заново поверх кешированных листингов и директив.
  Точно по построению.
- **R1** — мемо `resolveSourceUnder` и индекс ADDINCL. Запись зависит от существования одного
  пути. Для A/D-пути перебираются разбиения по слешам; если обе части есть в интерне, запись
  сбрасывается. Точно.
- **R2** — дети файла и search tier. Запись хранит хеш конфига, под которым получена.
  Переиспользуется, если файл не менялся, хеш совпал, ни один A/D-путь не оканчивается на
  target и результат в `$(B)` всё ещё зарегистрирован. Когда регистрируется выход, которого не
  было в базовом прогоне, сбрасываются записи с подходящим суффиксом. Изменение sysincl
  сбрасывает уровень целиком.
- **R3** — замыкания в mmap: пул бакетов и списки в образе, `Node.Inputs` ссылается прямо в
  него. Грязь распространяется по обратным рёбрам include от изменённых файлов на всех
  включающих — при загрузке из diff и в ходе прогона, когда пересчитанные дети разошлись с
  базой. Правка популярного заголовка сводится к пересчёту поверх готовых детей.

Открытое место — зависимость от первого дошедшего контекста: с diff порядок обхода может
измениться, и для членов переиспользованного замыкания это не проверить без обхода. Критерий
корректности: граф с образом и diff байт-в-байт равен графу чистого прогона на новом дереве;
проверяется на гейте синтетическими diff (правки заголовков, ADDINCL, добавление proto).

Формат рассчитывается сразу на R3 (решение 2026-11-19); порядок реализации — R0, R1, R2, R3.

## Интерфейс Tree

- Пространство имён: `listdir`, `exists*`, `isFile*`, `walk*`, `resolveSourceUnder*`, индекс
  ADDINCL.
- Факты о файле: `contentHash` без чтения, директивы include, токены ya.make, сырое `read` как
  крайний случай.
- С R2: дети и замыкания.

Tree заменяет: `GenCtx.fs`; чтение и `cache.parsed` в `IncludeParserManager`; `parsedFiles` на
уровне токенов; `contentHashes`, `sourceUnder`, `knownFiles`, `dirs` в OsFS; `addinclIndex`;
позже — source-часть `codegen.files` и хранилище `BucketCache`.

## Формат

Один файл: заголовок (magic, версия, id бинаря, проверка префикса констант, идентификатор базы,
таблица секций), секции выровнены по странице, массивы фиксированной ширины little-endian,
смещения вместо указателей. Запись — во временный файл, затем rename. Образ должен лежать на
локальном диске, не на FUSE.

Оценка размера для p12: около 1 ГБ без замыканий, около 1,5 ГБ с ними.

## Чего ждать

- FS: для неизменённых файлов ноль открытий; листинги перечитываются только у затронутых
  каталогов.
- Память: из кучи уходит около 1,1 ГБ интерна, с R3 ещё 504 МБ бакетов. maxrss считает и тронутые
  файловые страницы, поэтому анонимная память и куча Go меряются отдельно.
- CPU на in-memory FS (оценки по профилю, не измерения): R0+R1 — порядка 10% плюс доля GC; R2 —
  до 8%; R3 — до 5%.

## Риски

- Id-пространство при запуске на подмножестве целей: структуры, размеренные по `vfsBound`,
  вырастут до размера образа. Пока не оптимизируется (решение 2026-11-19).
- Полнота diff: неотслеживаемые файлы, удалённые после сборки образа, в diff не попадут.
- Обычный режим не должен замедлиться: каждый этап меряется A/B на sg5 и p12 без образа.

## Этапы

Каждый этап: граф p12 0/0 и sg5 байт-в-байт без образа; с образом — байт-в-байт с чистым
прогоном; замер CPU и памяти; коммит и пуш.

1. Интерн-таблица на зарезервированных диапазонах (байты, `id → смещение`, `lo`), без `cells`.
   Образа ещё нет. Сделано: `str_arena.go`, запись таблицы — `смещение | длина << 36` (64 ГиБ
   текста, строка до 256 МиБ). Замер на sg5 при GOGC=off: инструкции +0,04%, циклы +0,8%; по
   профилю прирост в `spliceBucketSlow` (раскладка кучи), строковые функции дешевле. Вариант с
   16-байтными заголовками строк давал −0,11% инструкций при тех же циклах и требовал бы
   фиксированного адреса или релокации образа.
2. Запись и загрузка образа со строками: глобальные флаги `--tree-out`, `--tree-image`, проверка
   префикса констант, замороженный индекс. Сделано: `tree_image.go` (заголовок 64 КиБ, секции
   выровнены на 64 КиБ), `MmapedIntMap`, `ReservedArena.mapFile`. Интернирование при
   инициализации должно быть детерминированным (обход map — только по отсортированным ключам),
   иначе отпечаток констант не совпадёт. p12: образ 882 МБ, повторный прогон берёт из него все
   7,1 млн строк и не добавляет ни одной; граф 0/0. CPU прежний: чтение, хеши и парсинг ещё не в
   образе.
3. Структура Tree над `FS`; секции content-hash и директив include: для неизменённых файлов нет
   чтения, хеша и парсера. Сделано: `tree.go` (Tree с явным полем `fs FS`, кеш разбора переехал
   в него из `SharedParseCache`), `MmapedFiles` (номер файла по id, хеши, записи разбора,
   директивы). Tree получают только `IncludeParserManager` и запись образа; executor получает
   читатель хешей `func(STR) uint64`; остальные потребители остаются на `FS`. Запись из образа
   отдаётся независимо от контекста, как и кеш внутри прогона (первый дошедший решает); сверка
   вида парсера ломала это правило и давала другой граф на p12. Образ привязан к бинарю хешем
   исполняемого файла. p12: образ 944 МБ, с ним 0 файлов разбирается заново, сырой граф `-G`
   побайтно равен графу без образа.
4. Токены ya.make, листинги, вход diff и битсеты валидности (R0 целиком).
5. R1: мемо `resolveSourceUnder` и индекс ADDINCL.
6. R2: дети и search tier.
7. R3: замыкания в mmap, обратные рёбра.
8. Diff из `.arc`/`.git` по commit из образа.
