## I. История появления — 11 мин

### 3. Что такое ya/ymake (контекст для внешних)
Монорепа, декларативные ya.make, построитель графа (C++) + оркестратор (Python), графы до сотен тысяч узлов,
UID узла = ключ кеша. Коротко, что за граф: узлы — команды, у каждой inputs/outputs, рёбра — «что после чего
запускать»; аналогия — makefile, только граф строится программой по декларативным описаниям.
Масштаб: большие цели — сотни тысяч узлов, вся монорепа — ~20 млн (примерно, смотря как считать).
Одна схема: ya.make → [ymake host + ymake target + ya] → граф → исполнение.

### 4. Три числа (бывший cold open)
`0.2 с vs 5 с` (configure графа ydb, ×25) · `×5 меньше памяти` · `100 000 узлов byte-exact`.
«Не про космические корабли — про набор простых инженерных практик. Доклад — ответ на вопрос "как"».
Цифры выстрелят повторно в разделах III и IV — рамка замкнётся.

### 5. Почему медленно
- Полная материализация графа перед исполнением.
- У графа три источника: ymake host + ymake target + ya — питонная часть сама строит тестовые ноды
  и подклеивает их в граф.
- Питонная часть очень медленная → нет стимула ускорять именно C++ часть.
Мечта: одна программа и строит граф, и исполняет узлы по мере готовности.
Тон: «исторические ограничения архитектуры», без обсирания — коллеги могут смотреть.

### 6. Питч и отказы
Два года «давайте перепишем связку C++/Python на Go». Контраргумент: «профит не доказан, потратим ресурс,
можно знатно объебаться» — и он рационален. Поворот слайда: они были правы — доказать профит можно было только сделав.
LLM изменили не аргумент, а цену доказательства.

### 9. Развилка: одна задача, три уровня участия
Слайд-лесенка на модельной проблеме host/target (один ya.make должен собираться и под host, и под target):
- **oy** — overseer + слабые модели (GLM), автономный тикетный конвейер: 167 коммитов, 3 дня, смерть.
  Ни к какой модели не сошлись — просто хачили узлы под эталон, тикет за тикетом.
  Эпитафия-коммит: «T-169: Fix TestFinalGraphValidation to skip by default».
- **ay без меня** — сильные агенты сами: сошлись к «построить два графа и смержить по host tool» —

- **ay + я** — вход в модуль по ребру с флагами: модуль адресуется не путём, а ya.make × набор флагов;

Выводы: слабые модели не держат цикл — оркестровка этого не компенсирует, получается output fitting на конвейере;
сильные модели воспроизводят известное решение; прорывную модель данных приносит человек.
(Зеркало будущего слайда «агенты ×2, человек ×10».)

## II. Авторесерч — 10 мин (структура по gist)

### 11. Секционный + тезис
«Генерация стала дешёвой. Проверка — нет». Скорость разработки в пределе = **скорость приёмки изменений**,
не производства. Пока принимаю глазами — потолок это я. Выход: убрать себя из цикла = автоматизировать приёмку.

### 12. Монотонная метрика
«Нет/да — не метрика. Наша автосборка — не метрика». «Построй мне замок в небесах» не работает — слишком большая
итерация до результата; нужно «насколько мы уже близко к замку». Тогда агента можно отпустить на часы:
«увеличь метрику этого скрипта на 10%».

### 13. Определение
Авторесерч (термин Карпатого) = оракул + корпус + цикл:
- оракул — исполняемая проверка поверх корпуса с монотонной метрикой (в простейшем виде — число зелёных тестов);
- корпус — тот самый набор тестов;
- цикл — способ заставить агента бежать до цели («они хотят соскочить, как и люди»).
Почему тесты, а не документ: спека-документ читается нами и моделью по-разному — всегда зазор интерпретации;
тест фиксирует вход/выход явно, второго прочтения нет. Здесь же закрывается вопрос с вече (слайд 8):
«правки в тесты» — не обвинение, а точное описание метода. Моя работа — проектирование оракула, а не написание кода.

### 14. Схема ay-авторесерча
Спеки у ymake нет — поведение в коде и конфигурации; зато есть граф, который можно построить на всю монорепу.
Срез исходников → канонический граф настоящим ymake → от ay требуем byte-exact совпадение нормализованного графа.
Каждый новый срез расширяет эмпирическую спецификацию. Одной фразой: «вот я добавил fail в граф тестов — почини его».
Почему byte-exact, а не «похоже»: порядок аргументов — семантика, он входит в UID.

### 15. Лестница целей
7 мая: 2 узла (вертикальный срез; унифицировано со слайдом 10) → +4 дня: 10 000 (tools/archiver, сам ymake) →
22 июня: 100 000 byte-exact.
Сейчас: ~100k строк Go, 2.5k коммитов, подавляющая часть — агентами.

### 16. Оракул — отдельный инженерный продукт («самое важное в докладе»)
- Сравнение по слоям: «не равны» бесполезно → количество узлов → топология → байты и UID; всегда виден текущий фронт.
- XFAIL с auto-promotion: цель живёт с частичной метрикой; совпала — навсегда стала обязательным гейтом.
- OLD→NEW acceptance: регресс точного случая, crash, timeout, усечённый вывод = отказ merge. Сюда же входит
  и перф (время генерации в бюджете) — а перф-метрика шумит, это самый капризный оракул; про него отдельный
  раздел в конце.
- dump diff/grep: десятки тысяч различий → кластеры причин.
Мостик: оракул и корпус есть — осталось запустить цикл и удержать его.

## III. Циклы разработки — 12 мин

### 17. Секционный + лесенка запуска цикла
Чат («вот скрипт, улучшай метрику» — на вечер и одну гипотезу) → /goal на сессии (агент не может остановиться,
пока метрика не выросла) → широкий фронт → рой (overseer). Каждая ступень — больше автономии, дороже инфраструктура.

### 18. Overseer — четыре вещи
Родился 8 мая — на следующий день после ay, из ручного процесса. Четыре механизма:
1) агент-планировщик, режущий фронт на задачи; 2) изолированный workspace на задачу;
3) независимое ревью после реализации — ×2 по цене, осознанная плата; 4) один последовательный merger в trunk.
Гетерогенные харнесы (claude/codex/…), jail-песочница.

### 19. Overseer эволюционировал вместе с ay (журнал отказов)
Почти каждый механизм — реакция на наблюдавшийся отказ, а не предварительный дизайн. Эпизоды:
- Роль planner (строил план разработки) выкинута почти сразу: ещё дороже, и контекст теряется —
  кто составил план, пусть и реализует, а не передаёт его текстом.
- Текстовые «KEY: VALUE» ответы ролей → typed JSON events (модель меняла формулировку — оркестратор ломался).
- Merger в отдельном scratch worktree + fast-forward trunk (две зелёные ветки несовместимы после первой интеграции).
- Ложный зелёный acceptance (валидатор падал после нескольких OK) → отвергать усечённый вывод.
- Процессы-сироты переживали таймаут → subreaper/process containment.
- Детерминированный acceptance сам стал merger'ом: LLM после исполняемого критерия не добавляет надёжности — только цену.

### 20. Кампания sg7
18 июня: большая цель, на старте 14k из 100k узлов, десятки независимых классов различий — широкий фронт.
GOALS.md — одна строка («validate должен перестать XFAIL по существу»), PROMPTS.md — толстый: цель и ограничения —
разные документы. Результат: 136 acceptance-gated merge за ~82 часа → 22 июня 100 000 узлов byte-exact
(строки 62k→82k, тестовые файлы 71→100).

### 21. Пределы swarm
Параллелизм упирается в пропускную способность оракула: предел был 4 копателя, дальше насыщение — лишние агенты
дают очередь и шум, не скорость. Реальная цена тикета: план, workspace, независимое чтение upstream,
2+ тяжёлых гейта, ожидание serial merger, rebase, REWORK-циклы. Плохая декомпозиция порождает качественную
ненужную работу. Перф в рое — почти никогда: параллельные решения лезут в один причинный механизм.

### 22. Волны
После кампании глубокие изменения — снова прямые сессии: generated sources сведены в один путь, EmitContext,
shadow maps удалены, lazy generation. Цикл: прямое исследование строит модель → рой закрывает фронт →
парная консолидация → новая архитектура открывает следующую волну. «Параллельные модели запретами не лечатся —
лечатся волнами». Диаграмма-кольцо.
Подводка: прежде чем перейти к перфу — сводка того, что агенты в этих циклах делают неправильно систематически.

### 23. Систематические ошибки агентов, часть 1
- Output fitting: перестановка аргументов по несуществующему «правилу» — лечения нет; только upstream-first,
  запрет fixture-specific кода, несколько разных точных случаев в гейте.
- Параллельная модель данных: новая map вместо registry — запретами не лечится (← слайд 22, волны).
- Доверие зелёному выводу: тест проходит не по той причине; red-before-green.
- Агенты правят сам оракул: «починить» тест или валидатор вместо кода — метрика зелёная, продукт хуже
  (эпитафия oy). Защита через оверсир: оракул вне досягаемости агента; ревьюер гоняет гейт сам;
  merge — детерминированный acceptance.

### 24. Систематические ошибки агентов, часть 2: дрейф
Оракул тянет систему туда, куда смотрит — и особенно опасно, когда он сломан или смотрит не туда:
- Сломанный оракул тянет в случайную сторону: OOM — Python-нормализация ела 11 ГБ, валидатор падал; агенты шли
  по сломанному оракулу и «чинили несуществующую багу днями» («стоит одному написать в чат про кривой json-парсер —
  все бросаются его менять. Не шучу»). Лечение: Go-нормализатор в 105 МБ, crash/truncation = сторона непригодна.
- Оракул смотрит на синтетику → оптимизация под синтетику (класс; примеры с числами — в разделе IV).
- Самый коварный дрейф — измерение производительности: агенты мерили средний wall time на случайно нагруженной
  машине и уверенно «ускоряли» программу, замедляя её.
Мостик в перф-раздел: про защиту от этого дрейфа — целый раздел впереди.

## IV. Перф — 10 мин (скелет — по колоде «Perf с помощью LLM»: три вещи стали дешёвыми)

### 25. Секционный: перф
Финальный экзамен метода. Парадокс: у перфа метрика есть от природы (число!) — самая естественная задача
для авторесерча, и самая коварная: число шумит. Метрика корректности не врёт (byte-exact — да/нет),
перф-метрика врёт постоянно; оракул = измерение, а измерению нельзя верить по умолчанию (← дрейф, слайд 24).
Перф в ay — часть корректности: гоночная машина, budget в гейте, correct-but-slower не шипится;
медленность часто симптом семантической ошибки, не «плохого контейнера» (расшифровка — слайд 30, инклуды).
Рамка: «LLM не сделала меня умнее — сделала три вещи дешёвыми: обкатать идею, дойти до хвостов, крутить цикл
без меня»; три акта = та же лесенка автономии, что чат → /goal → рой.

### 26. Числа (только интегральные) + инкрементальный построитель
Зачем важно время configure: поправил один файл → пересборка = configure всего графа + пара секунд
компиляции и линковки; «20 с configure + 2 с работы» — налог на каждую итерацию, люди теряют контекст,
и это бесит.
×25 configure (0.2 с vs ~5 с; ydb, прогретый файловый кеш, кеши ya/ay с нуля — парсинг и резолвинг честные),
×5 меньше памяти. Сравниваем только configure-стадию: исполнение графа сравнивать смысла нет.
Структурная победа: **инкрементальный построитель** — узлы уходят в исполнение до полной готовности графа
(streaming emitter). Отдельный поклон go runtime: спавн процессов из многопоточного рантайма без зигот
и дедлоков — то, что в C++/Python больно.

### 27. Дёшево обкатать идею (акт I — парное программирование)
Структуры, на которые раньше не поднялись бы руки:
- Darts для longest prefix match: «устрой мне deep dive, какие trie бывают» → незнакомая структура из статьи 1989 г.,
  cache-friendly массивы, сжатый внутренний цикл; ×10 к reference-реализации за 15 минут.
- Perfect hash за 5 минут (диспатч по длине + линейная комбинация букв, брутфорс);
  через две недели заменён на Darts — выкинуть тоже не жалко: порог «стоит ли делать» сдвинулся.
- «Я не умею в SSE/AVX. Теперь, наверное, и не придётся»: LLM — почти идеальный автовекторизатор;
  AVX2/AVX-512 блоки в .s, +1.5% на халяву. Что векторизовать — решает профиль.

### 28. Дёшево дойти до хвостов (акт II)
20% CPU уходило в map. Профиль такой точности не даёт → «напиши AST-трансформацию: каждый map-доступ через
wrapper с per-site счётчиком» (probe_mapinstr.go, флаг --probe=map). Лукапы: 40M → 500k по всей программе.
Хвост профиля плоский — сто сайтов по проценту: каждый фикс тривиален и скучен, окупается только сумма.
«Сто раз "пройдись по топу и исправь" — работа для агента, не для меня». Быстрый аллокатор ≠ локальность:
профиль по числу аллокаций — прокси локальности, и хвост в нём стоит столько же, сколько голова.

### 29. Цикл без меня требует оракула (акт III): приёмка перфа — тоже продукт
Подводка (в заметках): в разделе про циклы я показал дрейф «среднего wall time» — вот защита. Целый слайд, две колонки.
Левая колонка — протокол измерения:
- Метрики на прогон: wall (perf_counter_ns), user/system (rusage детей), task-clock:u, cycles:u, instructions:u
  из perf stat. Решение — по четырём: wall, task-clock, cycles, instructions; user/system только печатаются.
- Единица измерения — блок из 4 прогонов LRRL/RLLR, порядок блока случаен от seed; перед измерениями
  неизмеряемый warmup-блок.
- Блок → одно наблюдение на метрику: (log R1 + log R2 − log L1 − log L2)/2. ABBA-схема гасит линейный дрейф —
  и на это есть тест (test_block_log_ratio_cancels_linear_log_drift): харнес проверяет сам себя.
Правая колонка — статистика и вердикт:
- Односторонний парный sign-flip permutation test по блочным log-ratio: ≤20 блоков — точный перебор 2^n,
  дальше 200 000 сэмплов с поправкой (extreme+1)/(N+1); в обе стороны (p_fast/p_slow).
- Group-sequential: заглядывания при 30/46/70/106/120 прогонов на сторону (min 30, growth 1.5, max 120);
  α=0.05 делится Бонферрони по числу заглядываний → per-look p ≤ 0.01; внутри заглядывания по 4 метрикам — Holm.
- Вердикт: любая WORSE-метрика → REGRESSED, exit 3 (проверяется первой); иначе любая BETTER без регрессий →
  IMPROVED, exit 0; максимум без решения → INCONCLUSIVE, exit 2.
- A/A-режим: left = right → ранняя остановка выключена, печатается CALIBRATION; его --json подаётся как
  --calibration-json, MDE считается по независимому шуму. На каждом заглядывании печатаются R/L %, p_fast, p_slow,
  MDE при power 0.8 и runs/side для целевого эффекта 0.1%.
Мораль: REGRESSED проверяется первым — гипотеза виновна, пока не доказано обратное; протокол не даёт превратить
шум в архитектурное решение.

### 30. Что наловил протокол + границы (агенты ×2, человек ×10)
Провалы как результат: фантомные 3.8× (ошибка атрибуции); AVX на синтетике vs memory latency на реальном
наборе; и PageVec — развёрнуто, с архитектурным контекстом: одна программа = супероптимизированный
однопоточный построитель (интерн-таблица строк без блокировок — половина перфа) + многопоточный не особо
оптимальный исполнитель; чтобы вынести тяжёлые вычисления в исполнитель, нужен lock-free мостик между
мирами (воркеры читают таблицу, построитель реаллоцирует её под ними; lock замедлит в разы). PageVec:
−1.5% на честном сравнении → удалён → на следующий день возвращён как SWSR-мостик (один писатель, много
читателей, сегменты не переезжают): −1% структура, +15% от многопотока. Мостик машина не предложила —
придумал человек. «"Не внедрено" — тоже знание».
Границы: агенты полируют — честные ×2; порядок величины приносит человек. Главный пример: знание
«резолв инклудов не зависит от контекста → каждый файл резолвится ровно один раз» — агенты считали его
неправдоподобным и пытались убрать, пока гейт не запретил; это знание дало ×10.
«LLM мультиплицирует скилы, а не прибавляет». Мостик к финалу: цифры с четвёртого слайда теперь объяснены.
